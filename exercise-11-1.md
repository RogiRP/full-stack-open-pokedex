\# Ejercicio 11.1 - Calentando motores



Para esta reflexión, consideraré una aplicación web desarrollada en Python por un equipo de seis personas. En el ecosistema Python, las herramientas de CI están muy fragmentadas y cada una destaca en un aspecto concreto. Para el linting y análisis estático, Pyright es el mejor en verificación de tipos (escrito en TypeScript), aunque su autocompletado es deficiente; Microsoft reserva las capacidades más potentes para su extensión propietaria PyLance. Por otro lado, JEDI ofrece el mejor autocompletado para un lenguaje dinámico, y Ruff (escrito en Rust) está ganando popularidad por su velocidad. El enfoque más completo es PyLSP, un meta-servidor que integra JEDI, MyPy, Ruff y Rope (especializada en refactorización), aunque su plugin de MyPy ralentiza la verificación de tipos. Para pruebas, pytest es el estándar por su sintaxis simple y su sistema de fixtures, mientras que unittest viene incluido en la biblioteca estándar. Para pruebas end-to-end se usan Playwright o Selenium, y para BDD, Behave o Robot Framework. El empaquetado varía según el destino: Docker para contenedores web, PyInstaller o Nuitka (que compila a C) para ejecutables de escritorio, y Poetry para distribuir librerías en PyPI. Al ser Python interpretado, el concepto de "construir" no implica compilación, sino preparar el entorno y empaquetar dependencias.



Fuera de Jenkins y GitHub Actions, existen múltiples alternativas. Entre las integradas en repositorios destacan GitLab CI/CD (madura y con potente integración con Kubernetes), Bitbucket Pipelines (ideal si usas Jira) y Azure Pipelines (muy flexible para entornos híbridos). En la nube como SaaS están CircleCI (rápida, con excelente caché y paralelismo), Travis CI y Codefresh (enfocada en Docker/Kubernetes). En el mundo autoalojado moderno, Drone y Woodpecker son ligeros, usan YAML y ejecutan cada paso en contenedores aislados, consumiendo muchos menos recursos que Jenkins. Los precios varían: GitHub Actions ofrece 2000 minutos gratis, CircleCI 6000, y GitLab 400, mientras que las autoalojadas son gratuitas en software pero pagas la infraestructura.



Para este equipo de seis personas con una aplicación a punto de lanzarse, recomendaría decididamente una solución en la nube, salvo que existan restricciones legales extremas de datos. La razón principal es el costo de oportunidad: mantener un servidor propio (actualizar el SO, renovar certificados, gestionar discos llenos) consume tiempo de desarrollo que debería dedicarse a las funcionalidades críticas previas al lanzamiento. Además, la nube ofrece escalabilidad elástica: si la frecuencia de commits aumenta, se añaden más máquinas virtuales en segundos, mientras que un servidor autoalojado se saturaría y ralentizaría al equipo. El equipo no tiene un rol de DevOps dedicado, y los costos de los planes gratuitos o básicos de la nube son más que suficientes para este escenario. La integración nativa con GitHub Actions o GitLab CI (según dónde esté el código) es la opción más lógica, ya que no requiere configuraciones externas y su sintaxis YAML es el estándar actual. Si las pruebas se vuelven lentas, CircleCI sería una excelente alternativa por su sistema de caché avanzado.
